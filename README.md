# 企业文档知识库 RAG 智能问答系统

基于 Python 实现的检索增强生成（RAG）系统，支持 PDF / Word / txt / Markdown 文档的解析、
清洗、切分、向量检索与带引用的问答，并提供 FastAPI 接口服务与检索评测脚本。

## 功能

| 模块 | 文件 | 说明 |
|---|---|---|
| 文档解析与清洗 | `loader.py` | PDF / docx / txt / md，含表格提取与噪声行过滤 |
| 切分策略 | `splitter.py` | 固定窗口 / 按段落 / 按标题递归，三种可对比 |
| 向量化 | `embedder.py` | 智谱 embedding-3；无 Key 时自动降级为本地向量 |
| 向量存储与检索 | `store.py` | numpy 余弦相似度检索，可平滑替换为 Milvus / Chroma |
| RAG 问答 | `rag.py` | 检索 → 拼提示词 → 生成，强制引用来源，拒答未知问题 |
| 接口服务 | `api.py` | FastAPI，含参数校验、错误处理与日志 |
| 检索评测 | `evaluate.py` | 命中率评测，产出可写进简历的量化指标 |

## 快速开始

```bash
pip install -r requirements.txt

cp .env.example .env        # 填入 DEEPSEEK_API_KEY 和 ZHIPU_API_KEY

python main.py index                    # 建索引（默认按标题切分）
python main.py ask "年假有几天？"         # 提问
python main.py eval                     # 跑评测集，输出命中率
python main.py compare                  # 三种切分策略横向对比
```

启动接口服务：

```bash
uvicorn api:app --reload --port 8000
# 打开 http://127.0.0.1:8000/docs
```

## 设计说明

**为什么自己做向量存储而不是直接用 LangChain？**
语料规模在万级以内时，`numpy` 矩阵加余弦相似度就足够，而且能清楚看到检索的底层过程。
`store.py` 的 `load` / `search` 两个方法做了接口隔离，换成 Milvus 只需要改这两个方法。

**为什么 prompt 里强制要求引用来源？**
企业知识库场景下，无出处的回答等于没有价值。系统被要求"资料不足时直接说无法回答"，
这是抑制大模型幻觉最直接的手段。

**为什么做了三种切分策略？**
切分粒度直接决定检索命中率。切片过大噪声多，过小则语义不完整。
项目通过 `python main.py compare` 在同一评测集上横向对比三种策略，用数据而非感觉选择方案。

## 评测结果

自建 13 份企业文档语料（约 6000 字符）与 30 条中文问答评测集。
内容命中率 = Top-K 召回片段中包含答案关键词的比例；来源命中率 = Top-1 命中正确文档的比例。

向量模型：`BAAI/bge-m3`（SiliconFlow，1024 维）　Top-K = 4

| 切分策略 | 切片数 | 内容命中率 | 来源命中率 |
|---|---|---|---|
| fixed（固定窗口） | 27 | 93.3% | 93.3% |
| para（按段落） | 26 | **96.7%** | 93.3% |
| heading（按标题递归） | 95 | **96.7%** | 93.3% |

结论：固定窗口切分最差（会把句子从中间截断，破坏语义完整性）。
按段落与按标题递归两种策略内容命中率持平，但按标题递归产生的切片数是前者的
3.6 倍，索引体积与检索耗时更高。**在当前语料规模下按段落切分性价比最优。**

失败案例分析（2 条未命中）：
《员工手册》与《考勤与休假实施细则》都包含年假条款（5/10/15 天、提前 3 个工作日），
语义高度重叠，导致检索召回了错误文档。这暴露了纯向量检索在多文档重复内容场景
下的局限，也是引入 rerank 重排的直接动因。

### 重排（Rerank）效果

针对上面的失败案例，实现了**两阶段检索**：

- **第一阶段｜向量宽召回**：用 `bge-m3` 召回 `top_k × 3` 个候选（召得宽，保证不漏）
- **第二阶段｜交叉编码器精排**：用 `BAAI/bge-reranker-v2-m3` 对候选逐条打分，取 `top_k`

向量检索是"双塔"结构（query 与 doc 各自独立编码后算余弦相似度），快但精度有限；
重排把 query 和 doc 拼在一起送进模型，精度显著更高，代价是只能处理少量候选。

| 指标 | 仅向量召回 | 向量召回 + 重排 | 变化 |
|---|---|---|---|
| 内容命中率 | 96.7% | **100.0%** | +3.3% |
| 来源命中率（Top-1） | 93.3% | **100.0%** | +6.7% |

重排救回了 2 条原本召回错误文档的案例：「报销单需要谁签字」「离职时要归还什么」。

重排的价值不只体现在数字上——`bge-reranker` 给出的相关度分数区分度极高
（正确片段 0.79~0.98，无关片段 0.00~0.18），这让"资料不足时拒答"有了
可依据的阈值，而不是靠模型感觉。

> 复现命令：`python main.py rerank`、`python main.py compare`

> ⚠️ **语料规模决定结论可信度**。只放 2 份文档时三种策略命中率都是 100%，
> 因为随便召回 Top-4 都能覆盖答案，数字毫无意义。必须让语料中有足够多的
> **相似干扰项**（本项目的「采购审批 vs 报销审批」「员工手册年假 vs 考勤细则年假」
> 就是刻意构造的干扰），评测才能拉开差距。


## 待改进

- 未做多轮对话的上下文压缩，长会话会超出上下文窗口
- 向量库为单机 numpy 实现，未做分布式与增量更新
- 评测集规模偏小（30 条），结论的统计显著性有限
- 未利用重排分数的区分度做"低相关度直接拒答"的阈值策略
